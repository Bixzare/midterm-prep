Monitoring services: Prometheus and Grafana
32
Machine Learning in Production • Christian Kaestner & Bogdan Vasilescu, Carnegie Mellon University • Fall 2026
Prometheus is a time-series database and monitoring system originally built at SoundCloud around 2012, now a graduated (cloud-native computing foundation) CNCF project (same foundation as Kubernetes). Pull-based metrics collection; scrapes HTTP endpoints that services expose via instrumentation that exposes a /metrics endpoint. Prometheus pulls from those endpoints on a schedule, typically every 15–30 seconds.
Data model:  labeled time series. Every metric has a name and a set of key-value labels. Has a query language, can compute rates, percentiles, and aggregations over those time series.
Four metrics types: counters, gauges, histograms, summaries

Grafana: visualization and dashboarding layer that sits on top of Prometheus (and many other data sources). It doesn't collect or store any data itself.  Makes it easy to create real-time dashboards with auto-refresh, set up alerting thresholds.
Prometheus: "what's happening right now and over the last N hours/days”;  traditional experiment tracking tools like MLflow and W&B answer "how did this model perform during training and offline evaluation."  Prometheus/Grafana close the loop by tracking the model after it's deployed.
Prometheus is designed for operational metrics, not high-cardinality data. Don’t log individual prediction; use a logging pipeline. Better for aggregate signals.

Engineering Challenges for Telemetry
Data volume and operating cost
e.g., record "all AR live translations"?
reduce data through sampling
reduce data through summarization (e.g., extracted features rather than raw data; extraction client vs server side)
Isolating feedback for specific ML component + version
Biased sampling / Rare events
Privacy (related: Offline deployments)
44
Machine Learning in Production • Christian Kaestner & Bogdan Vasilescu, Carnegie Mellon University • Fall 2026
Data volume and operating cost. Google Translate processes something on the order of 100 billion words a day; can’t record all inputs/outputs. Sampling vs. summarization tradeoff: Sampling means keeping, say, 1% of raw requests at random, which preserves individual examples you can inspect later but may miss rare events. Summarization means computing aggregates on the fly, like "average confidence score per minute" or "distribution of predicted classes this hour," and only storing those.
Client-vs-server-side: extracting features or computing summaries on the device reduces bandwidth and server cost, but you lose the ability to reprocess raw data later.
Isolating feedback for specific ML component + version (e.g., search engine with a query understanding model, a ranking model, and a re-ranking model), user feedback like "I didn't find what I wanted" is about the whole pipeline. If you just rolled out v3 of the ranking model but v2 of query understanding is still running, you need your telemetry tagged with version metadata so you can slice results accordingly.  Connects to feature flags. Also especially tricky for agentic systems/LLMs (rags, etc).
Biased sampling / rare events. Uniform random sampling sounds fair, but systematically underrepresents rare classes. In practice, teams use stratified sampling (over-sample low-frequency categories) or trigger-based logging (log the full request whenever the model's confidence is below a threshold, or whenever two models in a shadow deployment disagree). (consider telemetry strategies).
Privacy. Design tension (also don’t collect what you don’t need). Better telemetry means better models, but bad for privacy. Concrete techniques include differential privacy for aggregated metrics, on-device summarization, and federated evaluation.
"offline deployments": some ML systems run entirely on-device (medical devices, military, industrial settings with no connectivity), so you can't do any real-time telemetry at all. Those systems have to rely on periodic sync or purely offline evaluation, which is a fundamentally different engineering constraint.

Analyzing Results: Stats 101
All the data have some distribution.
Normal distribution is very common (e.g. students tend to get average score, not full score).
When we draw samples from the same distribution, we can get different samples just by chance.
Statistics tells us whether “interesting" patterns we observe actually exist in the samples, or whether it’s just sampling noise — use some numbers to express uncertainty.
Confidence interval: if we can compute the average of some samples (average on-site time of 10 users), what’s the average of the population (whole user group)?

Analyzing Results: Stats 101
Significance testing also helps with comparison. When most of the confidence intervals overlap, we’d know there’s no actual differences between groups.
This is quantified by p-value:
Misconception: “what is the probability a difference between two samples is by chance?” (lower = higher likelihood of a sig. difference)
Reality: the p-value starts with the assumption that there's no real difference (null hypothesis), then asks "how likely would our observed data be in that scenario?"

Conditional probability confusion: A p-value of 0.03 doesn't mean there's a 3% chance the difference is due to chance. It means that if there were no real difference, we'd see data this extreme only 3% of the time.�The p-value can't tell us the probability of our hypothesis being correct because it assumes one particular hypothesis (no difference) from the start.

Stats 101: How to compute p-value?
Parametric tests: Assume comparing normally distributed groups that have the same variances.
Tests: t-test, ANOVA, & linear regression.
For: model accuracy, human click streams
More sensitive and powerful when the requirement is met.
Non-parametric tests: Does not assume normal distribution.
For: categorical data like Likert Scale rating
Tests: Wilcoxon signed-rank test compare users’ nominal Likert Scale ratings
