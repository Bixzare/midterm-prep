Pydantic checks data against a Python class
1 · You write a class
Field names with Python types. The class is the schema.
2 · Pydantic parses data into it
JSON or a dict goes in, a typed Python object comes out. "36" becomes the number 36.0.
3 · Or it raises ValidationError
One entry per problem: which field, and what is wrong with it.
Pydantic is a Python library; web frameworks and LLM libraries accept its classes.
from pydantic import BaseModel

product: str
quantity: float
unit: str

Machine Learning in Production • Christian Kaestner & Bogdan Vasilescu, Carnegie Mellon University • Fall 2026
Pydantic is a Python library for checking data. You describe the data you expect as a class: each field gets a name and a Python type. Then you hand Pydantic some data, here a JSON string, with model_validate_json. If the data fits, you get back an ordinary Python object whose fields have the right types: quantity is the float 36.0, even though the JSON had the string "36", because Pydantic converts values when the conversion is safe. If the data does not fit, Pydantic raises a ValidationError that lists every problem at once, with the field and a message: "fifty" is not a number, and unit is missing. Many tools accept a Pydantic class as the description of the data they should produce or accept, including FastAPI and the SDKs for calling LLMs. We use it for both on the next slides. LineItem here is a cut-down version of the one in the demo; the next slide shows the full one. (Output on the slide is from Pydantic 2.13, shortened.)

class LineItem(BaseModel):  # one product in the delivery
model_config = ConfigDict(extra="forbid")  # no unknown fields
product: str
quantity: float
unit: Literal["count", "kg", "liter"] = Field(  # one of these
description="convert lb to kg, gallons to count")
@model_validator(mode="after")  # our own check
def plausible(self):
if self.quantity <= 0:
raise ValueError("quantity must be positive")
if self.unit == "count" and not self.quantity.is_integer():
raise ValueError("not a whole number of items")
return self

class DeliveryNotice(BaseModel):
supplier: str
delivery_date: date
items: list[LineItem]  # one LineItem per product
For each e-mail, the LLM fills in one DeliveryNotice, with one LineItem per product.
SHAPE → JSON SCHEMA
Types, allowed units, required fields, no extra fields
Pydantic writes them out as a JSON schema, which the LLM gets with the request (response_format). Some LLM APIs enforce it, some do not.
MEANING → VALIDATORS
Positive quantities; whole numbers for count
These rules are Python code, so the JSON schema leaves them out. Pydantic checks them on every line item when it parses the answer.
Machine Learning in Production • Christian Kaestner & Bogdan Vasilescu, Carnegie Mellon University • Fall 2026
DeliveryNotice is our class, not part of Pydantic. It describes what we want the LLM to extract from a supplier's delivery e-mail: who delivers, when, and one LineItem per product. The code uses three things the last slide did not show. Literal lists the allowed values. extra="forbid" rejects fields we did not ask for. A method marked @model_validator is our own check; Pydantic runs it after the type checks and turns a ValueError raised there into a ValidationError. The class has two kinds of rules. The blue lines describe the shape: field names, types, allowed units, no extra fields. Pydantic turns them into a JSON schema with model_json_schema(), and passing response_format=DeliveryNotice sends that schema to the LLM. Some providers enforce the schema while the LLM writes its answer, others do not, so we check the answer anyway. The orange lines describe meaning: a quantity must be positive, and a count must be a whole number. These rules are Python code, so the JSON schema leaves them out and the LLM never sees them. Pydantic checks them on each line item when it parses the answer, and an error path such as items.1.unit points at the second line item.

extract.py runs this loop. The e-mail goes to the LLM with response_format=DeliveryNotice. We parse the answer with DeliveryNotice.model_validate_json(answer). If Pydantic raises a ValidationError, we append the LLM's answer and a user message "Your answer is not valid: [the errors]. Return a corrected JSON object." and ask once more. The error messages are precise (field path plus what is wrong), so the LLM can often fix its own output. If the second answer is still invalid, the e-mail goes to out/quarantine.json for a human. A valid notice then goes through one check Pydantic does not do: each product name is fuzzy-matched against our catalog, and a name that scores below 90 is quarantined too. Only then does the notice reach the inventory.

Apache Avro: a schema for events sent between programs
Each checkout terminal sends one event per receipt line. The events go through Kafka, a message broker: producers (the terminals) write events to it, and consumers (inventory, forecasting, …) read them.
1 · The schema is a JSON file
Producers and consumers agree on it. It names each field and its type.
2 · Every write is checked
The Avro writer rejects an event that does not fit the schema.
3 · The data is compact binary
A reader needs the schema to decode it, so the schema travels with the data or is kept in a registry.
{"type": "record", "name": "SaleEvent",
"fields": [
{"name": "event_id", "type": "string"},
{"name": "event_time", "type": {"type": "long",
"logicalType": "timestamp-millis"}},  // ms since 1970
{"name": "store_id", "type": "int"},
{"name": "terminal_id", "type": "string"},
{"name": "product_id", "type": "int"},
{"name": "quantity", "type": "double"},  // a float
{"name": "unit", "type": {"type": "enum", "name": "Unit",
"symbols": ["count", "kg", "liter"]}},  // one of these
// an exact decimal with 2 digits after the point
{"name": "unit_price", "type": {"type": "bytes",
"logicalType": "decimal", "precision": 8, "scale": 2}},
// used when an event has no promo
{"name": "promo", "type": "boolean", "default": false}
]}
Machine Learning in Production • Christian Kaestner & Bogdan Vasilescu, Carnegie Mellon University • Fall 2026
Setting: the supermarket's checkout terminals produce a stream of sale events, one per receipt line. In a real system they go through Kafka, a message broker, and several programs read them. Those programs need to agree on what an event looks like, and Avro is one common way to write that agreement down. The schema is plain JSON: a record called SaleEvent with nine fields. Most types are simple (string, int, double, boolean). Three are richer: event_time is a timestamp stored as milliseconds, unit is an enum with three allowed values, and unit_price is an exact decimal with two digits after the point. promo has a default of false; defaults decide which schema changes are safe (two slides on). The data itself is binary, without field names, so it is small, and nobody can read it without the schema.

An anomaly detector learns what typical rows look like and scores each row by how far it is from them. It has no information about a delivery beyond the features we give it. With the quantity alone, every delivery is compared with all others: products that always come in large numbers get high scores, and small wrong deliveries get low ones. Adding one feature, how far this quantity is from the usual quantity of this product in this store, lets the detector compare like with like. That feature raises precision by more than 20 points for both detectors; switching between detectors changes it much less. It works because a store receives similar amounts of a product again and again. A third detector, LOF, fails on this data (0.4%): it compares how crowded each point's neighborhood is, and thousands of deliveries with exactly the same quantity make that comparison useless here.

Near-duplicate detection is also called record linkage: deciding whether two records describe the same thing. Splink is one library for it, next to Dedupe and Zingg on the lecture slide. It compares each pair of rows field by field. A field that matches adds evidence, a field that differs removes some, and the sum becomes a probability. On this data it grouped the wrong rows until we set two weights from domain knowledge: a real duplicate has the same store and product in 99.9% of cases. A higher threshold flags fewer wrong pairs and finds fewer duplicates; at 0.3 it finds only 39.
